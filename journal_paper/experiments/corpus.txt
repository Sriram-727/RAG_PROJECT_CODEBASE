CHAPTER 1: INTRODUCTION
1.1 BACKGROUND AND MOTIVATION
Large Language Models (LLMs) have demonstrated transformative capabilities across natural language comprehension, automated code synthesis, clinical decision support, and complex multi-step reasoning. Despite remarkable linguistic fluency, standalone parametric LLMs remain fundamentally constrained by static pre-training knowledge cutoffs, an inability to inspect private corporate repositories, and a persistent tendency to fabricate plausible yet unverifiable statements—a phenomenon formally designated as factual hallucination [1]. In mission-critical enterprise domains such as legal contract analysis, financial auditing, and medical informatics, ungrounded generative outputs pose severe operational and regulatory risks.

Retrieval-Augmented Generation (RAG) has emerged as the de facto architectural paradigm for overcoming parametric limitations by retrieving semantically relevant document segments from an external knowledge index and injecting those segments directly into the inference context window of the generative model [1]. In a standard RAG workflow, unstructured enterprise documents are segmented into text chunks, converted into high-dimensional dense semantic vectors via neural embedding transformers, and stored within specialized vector databases. When a user submits a natural language query, the system embeds the query into the same metric space and executes an Approximate Nearest Neighbor (ANN) search to fetch the top-K most relevant chunks.

Because maintaining multi-gigabyte or terabyte-scale high-dimensional vector indices and orchestrating sub-second ANN searches require substantial random-access memory (RAM) and parallel compute infrastructure [2, 3], organizations routinely offload the vector storage and retrieval tier to commercial Database-as-a-Service (DBaaS) and cloud vector providers such as Amazon Web Services (AWS), Google Cloud Platform, Pinecone, or Qdrant Cloud. While cloud outsourcing eliminates local hardware maintenance and provides elastic scalability, delegating proprietary enterprise knowledge bases and similarity search execution to third-party cloud environments introduces a critical trust and security dilemma [4].

Conventional cloud vector databases require either plaintext document payloads or unmasked floating-point embeddings to build navigable proximity structures such as Inverted File (IVF) clusters and Hierarchical Navigable Small World (HNSW) graphs [2, 3]. Recent breakthroughs in adversarial machine learning have proven that dense semantic embeddings are not irreversible cryptographic hashes; rather, vector representations encode nearly as much sensitive information as raw text [5]. Furthermore, because commercial cloud servers operate as opaque black-box environments, a client organization possesses no native cryptographic mechanism to verify whether returned search results are authentic, untampered, and complete. Bridging the gap between high-speed cloud vector retrieval and mathematical data security motivates the design of the Asymmetric Verification Framework presented in this report.
1.2 PROBLEM STATEMENT
Outsourcing enterprise vector indexing and similarity search to untrusted commercial cloud infrastructures exposes the retrieval pipeline to five interconnected security and performance vulnerabilities. Figure 1.1 illustrates the structural vulnerability points across a conventional cloud-assisted RAG lifecycle.

Fig 1.1: Structural Vulnerability Points in Conventional Cloud-Assisted RAG Pipelines

As depicted in Fig 1.1, transitioning from raw enterprise documents to a grounded generative response over an untrusted network raises five specific technical problems:

Confidentiality Breakdown and Embedding Inversion: Uploading plaintext document chunks or unmasked dense semantic embeddings exposes confidential intellectual property, trade secrets, and personal records to untrusted cloud operators. State-of-the-art embedding inversion attacks, such as Vec2Text [5], demonstrate that raw floating-point embeddings can be inverted back into near-exact cleartext sentences via iterative hypothesis refinement. Concurrently, semantic membership inference attacks such as S2MIA [6] exploit generative outputs to deduce whether specific proprietary records reside within the retrieval corpus.
Opaque and Untrusted Cloud Execution: Commercial cloud vector servers function as black-box environments that may behave as honest-but-curious adversaries, suffer internal privilege escalation, or experience silent index corruption without notifying client applications [4].
Unverifiable Retrieval Integrity: Standard vector databases return top-K candidate chunks without any cryptographic proof of origin. A compromised cloud server or man-in-the-middle adversary can maliciously splice, modify, or forge retrieved context chunks to poison downstream LLM generation without client detection.
Silent Cluster Omission Attacks: In partitioned vector indices such as IVF Voronoi clusters or HNSW proximity graphs [2, 3], a resource-rational ("lazy") or cost-cutting cloud provider can selectively skip probing computationally dense partitions to conserve server CPU and RAM cycles. Omitting boundary clusters silently degrades retrieval recall and induces factual hallucinations in the LLM response.
Zero-Knowledge Proof (ZKP) Proving Cost: Existing academic proposals for verifiable vector search—including VeriRAG [7], V3DB [8], and zkRAG [9]—rely on zero-knowledge succinct non-interactive arguments of knowledge (zk-SNARKs) over Rank-1 Constraint Systems (R1CS) or Fully Homomorphic Encryption (FHE). Server-side proof generation remains expensive. The authors report about 50 s per HNSW query for zkRAG [9] (10^6 vectors, 128 dimensions, single thread), a prover time of 96 s and a verifier time of 3 s for VeriRAG [7] on a 37 GB dataset, and 5.90–11.57 s of proving for VERIF [25] on 8–32 million vectors, while verification costs range from milliseconds (V3DB [8]) to about 1–3 s. Even the fastest of these proving times is well above the sub-2-second end-to-end response that interactive enterprise RAG workflows expect.

1.3 OBJECTIVES
The primary objective of this project is to design, implement, and empirically validate an Asymmetric Verification Framework for cloud-assisted RAG systems that achieves cryptographic security with sub-30-millisecond verification latency. The specific technical objectives are:

To establish an asymmetric, zero-knowledge-proof-free trust boundary between a lightweight trusted client enclave and an untrusted commercial cloud vector engine, isolating all cryptographic keys and master state roots strictly within the client domain;
To formulate an isometric orthogonal vector masking transformation using QR decomposition paired with secret coordinate permutation that preserves exact inner products and cosine similarity rankings on the cloud while making Vec2Text embedding inversion substantially harder for an adversary who observes only masked data;
To construct an append-only, Two-Tier Merkle Mountain Range (MMR) auditing structure comprising per-tenant User MMRs (Tier 1) and a unified Cloud Enterprise MMR (Tier 2) capable of generating and verifying O(log N) cryptographic inclusion proofs;
To develop an algebraic Voronoi Dynamic Boundary Validation (DBV) protocol utilizing a 1.5 × r_closest multi-probe cosine margin expansion to detect lazy-cloud cluster omission by requiring verifiable evidence for every cell the cloud must probe (Section 3.5); the 1.5 factor is justified by a margin ablation over 1.2, 1.5 and 2.0 measuring recall, cells probed and false-alarm rate on honest runs ;
To integrate a deterministic five-gate sequential client verification pipeline combining Role-Based Access Control (RBAC), MMR integrity auditing, DBV completeness checking, AES-256-GCM authenticated decryption, and Corrective RAG (CRAG) / Self-RAG reflection prior to LLM synthesis; and
To benchmark the complete framework against state-of-the-art zk-SNARK verifiable RAG baselines and evaluate tamper detection across normal and adversarial operational scenarios.
1.4 PROPOSED SYSTEM OVERVIEW
Rather than forcing untrusted cloud servers to compile heavy arithmetic zero-knowledge circuits, the proposed Asymmetric Verification Framework shifts the cryptographic root of trust and lightweight verification burden to a trusted client enclave. The system decouples RAG execution into an offline document ingestion and indexing phase (Phase A) and an online query retrieval and verification phase (Phase B), orchestrated across six modular pipelines:

Module 1 (Local Ingestion and Hierarchical Chunking): Ingests multi-format enterprise documents (PDF, DOCX, TXT) within the client enclave and segments text into coarse-grained parent chunks (800–1,200 characters) for LLM context synthesis and fine-grained child chunks (200–300 characters) linked via bidirectional metadata pointers for dense indexing.
Module 2 (Privacy Transformation Engine): Generates L₂-normalized 384-dimensional dense embeddings locally using models such as BAAI/bge-small-en-v1.5 or all-MiniLM-L6-v2, masks vectors via a secret orthogonal matrix Q and coordinate permutation π, and encrypts plaintext chunks using AES-256-GCM authenticated encryption [11].
Module 3 (Two-Tier Trust Structure Builder): Computes domain-separated SHA-256 leaf digests binding chunk metadata and plaintext hashes, appends leaves to per-tenant Tier 1 User MMRs, and bags tenant peaks into a global Tier 2 Cloud Enterprise MMR anchored by a local 32-byte root R_ent [12, 13].
Module 4 (Cloud Indexing and Multi-Probe ANN Search): Stores only masked vectors, AES-256-GCM ciphertexts, and structural MMR mirror nodes inside the untrusted cloud engine (Qdrant/FAISS), executing multi-probe ANN search over Voronoi IVF clusters and HNSW graphs [2, 3].
Module 5 (Dynamic Boundary Validation): Audits search completeness inside the client enclave by computing exact cosine distances between the query vector and local Voronoi coarse-quantizer centroids, verifying that the cloud supplied evidence for every mandatory boundary cluster within a 1.5 × r_closest margin.
Module 6 (Five-Gate Sequential Client Verifier and Grounded Synthesis): Enforces RBAC tenant isolation, Two-Tier MMR inclusion proof verification, DBV completeness validation, AES-256-GCM tag decryption, and CRAG/Self-RAG relevance reflection [14, 15] before passing verified context to the generative LLM (Ollama, Groq, or Gemini).
1.5 SCOPE OF THE PROJECT
The scope of this project encompasses the architectural design, mathematical formulation, software implementation, and empirical security evaluation of the Asymmetric Verification Framework for text-based enterprise RAG repositories. The client enclave and verification engine are implemented in Python 3.11 using FastAPI, PyTorch, NumPy, scikit-learn, and the standard cryptography package, interfacing with Qdrant and FAISS vector backends. Dense semantic representations are standardized on 384-dimensional normalized embeddings (BAAI/bge-small-en-v1.5), and generative synthesis is validated across local Ollama models as well as cloud-hosted Groq and Gemini APIs.

The framework operates under the foundational assumption that the client enclave (an enterprise security gateway or local workstation) securely safeguards the master secret tuple K_client = {Q, π, K_AES, R_ent} against local operating system compromise. Voronoi coarse-quantizer centroids are trained during batch indexing cycles. Hardware-level enclave integration via Intel SGX or ARM TrustZone Trusted Execution Environments (TEEs) and streaming real-time centroid re-clustering without re-masking are designated as extensions outside the current implementation scope.

CHAPTER 2: TRADITIONAL METHODS
2.1 CONVENTIONAL CLOUD VECTOR RETRIEVAL AND CRYPTOGRAPHIC SCHEMES
Modern enterprise Retrieval-Augmented Generation systems rely on Approximate Nearest Neighbor (ANN) indexing structures to search millions of high-dimensional embedding vectors in sub-linear time [2, 3]. Because exact exhaustive K-Nearest Neighbor (K-NN) search scales linearly as O(N · d) for N vectors of dimension d, production vector engines such as FAISS [2] and Qdrant employ space-partitioning and graph-traversal heuristics. The two predominant indexing paradigms are Inverted File (IVF) indexing, which partitions the metric space ℝᵈ into C Voronoi cells using K-Means clustering [2], and Hierarchical Navigable Small World (HNSW) graphs, which construct multi-layered proximity graphs supporting logarithmic greedy routing [3].

When enterprises deploy IVF or HNSW indices on third-party cloud infrastructure, protecting data confidentiality and query integrity requires cryptographic intervention. Historically, four broad cryptographic families have been applied to outsourced database search:

Symmetric Property-Preserving and Order-Preserving Encryption (PPE/OPE): Encrypts scalar values while preserving relative ordering for range queries [16]. However, PPE and OPE leak statistical distribution profiles and cannot evaluate multi-dimensional Euclidean norms or cosine similarities in ℝᵈ.
Fully Homomorphic Encryption (FHE): Schemes based on Ring Learning With Errors (RLWE), such as CKKS [17], permit arbitrary addition and multiplication directly over ciphertexts. While FHE provides strong semantic security, evaluating homomorphic inner products and non-linear top-K comparisons across hundreds of thousands of 384-dimensional vectors incurs multi-second to multi-minute latency per query and expands ciphertext storage by orders of magnitude.
Trusted Execution Environments (TEEs): Hardware enclaves such as Intel SGX isolate vector computation inside encrypted CPU memory pages [26]. Although TEEs achieve near-native execution speeds, commercial cloud TEEs remain vulnerable to microarchitectural side-channel attacks (e.g., Foreshadow, Plundervolt), page-fault leakage, and restricted enclave Page Cache (EPC) memory limits that force costly paging during large HNSW graph traversals.
Zero-Knowledge Succinct Non-Interactive Arguments of Knowledge (zk-SNARKs): Cryptographic proof systems (such as Groth16 [19] and Plonk [20]) allow an untrusted prover (the cloud server) to convince a verifier (the client) that a computation y = F(x, w) was executed correctly without revealing the witness w. However, translating floating-point cosine distance calculations and priority-queue sorting into finite-field arithmetic circuits over Rank-1 Constraint Systems (R1CS) creates millions of multiplication gates, resulting in severe prover memory and latency bottlenecks.

2.2 EARLIER PRIVACY-PRESERVING AND VERIFIABLE RAG APPROACHES
Research specifically targeting the security of cloud-hosted Retrieval-Augmented Generation spans four primary technical thrusts: distance-preserving vector encryption, membership inference defense, edge-cloud split execution, and zero-knowledge verifiable retrieval. Figure 2.1 presents the taxonomy of existing privacy-preserving and verifiable RAG architectures.

Fig 2.1: Taxonomy of Privacy-Preserving and Verifiable Retrieval Architectures

As categorized in Fig 2.1, each branch of the literature addresses an isolated subset of the cloud RAG threat model:

Distance-Preserving Vector Encryption: In the domain of vector confidentiality, Ye et al. [21] proposed ppRAG, a privacy-preserving RAG framework utilizing distance-preserving matrix encryption to execute ANN search directly on cloud infrastructure without resorting to computationally expensive Homomorphic Encryption. While ppRAG effectively conceals raw vector coordinates against passive eavesdroppers, the framework provides no cryptographic mechanism to audit retrieval integrity or search completeness, leaving the client vulnerable to forged ciphertexts, cross-document chunk splicing, or omitted search partitions.
Membership Inference Defense and Differential Privacy: Addressing inference-time privacy leakage, Li et al. [6] introduced S2MIA, demonstrating that black-box adversaries can exploit semantic similarity between generated LLM responses and target candidate records to mount high-accuracy membership inference attacks against RAG knowledge bases. To counter such leakage, Grislain [22] developed DP-RAG, which injects calibrated differential privacy (DP) noise into token logits during generative decoding. However, injecting DP noise noticeably degrades factual precision in domain-specific enterprise tasks, and the cumulative privacy budget (ε) depletes rapidly under continuous organizational querying [22].
Zero-Knowledge Verifiable Retrieval: To counter untrusted server execution, recent cryptographic studies have attempted to apply Zero-Knowledge Proofs to database and vector queries. Li et al. [23] proposed ZKSQL, utilizing zero-knowledge polynomial commitments to verify relational SQL query evaluations; however, discrete relational set operations (joins, group-by, equality filters) cannot scale to continuous high-dimensional metric spaces where similarity is governed by floating-point inner products. For graph-based retrieval, Wu et al. [24] proposed ZKGraph, which decomposes graph queries into expansion-centric operators for zero-knowledge circuit evaluation, though this approach targets general graph databases and is not designed for dynamic HNSW proximity graphs [3, 24].

Targeting vector RAG pipelines specifically, VeriRAG [7] formulated algorithm-specific zero-knowledge arguments to verify top-K ANN results without exposing the underlying dataset. Similarly, V3DB [8] standardized Inverted File with Product Quantization (IVF-PQ) search bound to cryptographic database snapshots via audit-on-demand zk-SNARKs. Concurrently, zkRAG [9] constructed a succinct zero-knowledge argument for HNSW-based retrieval over a committed database and index. While VeriRAG, V3DB, and zkRAG provide strong soundness guarantees, their proving cost remains substantial, and each paper reports its own figures: VeriRAG reports a prover time of 96 s and a verifier time of 3 s on a 37 GB dataset [7]; V3DB reports proving up to about 22× faster and peak memory up to about 40% lower than a circuit-only baseline, with millisecond-level verification [8]; and zkRAG reports about 50 s to prove a typical HNSW query over 10^6 vectors of dimension 128 on a single thread [9]. The closest competitor, VERIF [25], is a zero-knowledge proof system for IVF-Flat retrieval that proves retrieval over 32 million and 8 million vectors in 5.90 s and 11.57 s, with verification taking 0.62–1.48 s and peak memory up to 99.1% lower than a Plonky2 baseline. Unlike the framework proposed here, these systems prove the full retrieval computation, whereas this work verifies protocol compliance on the client. A comprehensive security taxonomy by Palanisamy et al. [4] further confirmed that existing RAG defenses remain fragmented across confidentiality, integrity, and availability pillars.

2.3 FOUNDATIONAL MATHEMATICAL AND CRYPTOGRAPHIC PRELIMINARIES
To overcome the operational drawbacks listed in Table 2.2, the proposed Asymmetric Verification Framework synthesizes five foundational mathematical and cryptographic primitives:

Merkle Mountain Ranges (MMR): Crosby and Wallach [12] introduced history trees for tamper-evident logging; the Merkle Mountain Range itself is Peter Todd's design [13], used for append-only commitments such as blockchain state. An MMR is an append-only collection of perfect binary Merkle trees ("mountains") arranged in strictly decreasing order of height. Because completed subtrees never change, inclusion proofs issued earlier stay valid as new leaves are appended, and MMRs support O(1) amortized leaf appending and O(log N) inclusion proof generation by "bagging" the peaks of individual mountains into a single 32-byte cryptographic root.
Voronoi Tessellation and Inverted File (IVF) Indices: High-dimensional vector search engines partition the metric space ℝᵈ into C disjoint Voronoi cells Ψ₁, Ψ₂, …, Ψ_C governed by coarse quantizer centroids {μ₁, μ₂, …, μ_C} trained via K-Means clustering [2]. Formally, each cell Ψ_i contains all points in ℝᵈ closer to centroid μ_i than to any other centroid μ_j (j ≠ i). During multi-probe ANN search, a query vector probes the closest primary Voronoi centroid alongside adjacent boundary cells to prevent recall degradation near cell borders.
Isometric Orthogonal Transformations: A real square linear operator Q ∈ ℝ^{d × d} belonging to the orthogonal group O(d) satisfies the algebraic identity Qᵀ Q = Q Qᵀ = I_d, where I_d is the d × d identity matrix and det(Q) = ±1. Because orthogonal transformations are Euclidean isometries, applying Q strictly preserves Euclidean vector norms (║Qu║₂ = ║u║₂) and inner products (⟨Qu, Qv⟩ = ⟨u, v⟩). Consequently, exact cosine similarity rankings can be evaluated directly within the transformed cloud domain while concealing raw semantic coordinates behind d(d-1)/2 continuous rotational degrees of freedom. In this work Q is the orthogonal factor of the QR decomposition of a random Gaussian matrix, with the column signs corrected using the diagonal of R so that Q is Haar-distributed (uniform on O(d)); this is what makes Q a properly random secret.
AES-256-GCM Authenticated Encryption: Standardized in NIST Special Publication 800-38D [11], the Advanced Encryption Standard in Galois/Counter Mode (AES-256-GCM) provides Authenticated Encryption with Associated Data (AEAD). The cipher combines counter-mode (CTR) symmetric stream encryption using a 256-bit secret key and a 96-bit Initialization Vector (IV) with a 128-bit Galois Message Authentication Code (GMAC) tag computed over the universal hash function GHASH. Any unauthorized bit modification to the ciphertext or associated metadata invalidates the 128-bit GMAC tag prior to plaintext release.
Corrective and Self-Reflective RAG Grounding: Even when retrieved document chunks are cryptographically authentic and complete, irrelevant or ambiguous passages can degrade LLM synthesis [14, 15]. Corrective RAG (CRAG) [15] evaluates the semantic relevance of retrieved chunks against the user query to filter out noisy context, while Self-RAG [14] incorporates self-reflection criteria to verify that generated statements are strictly supported by the retrieved evidence.
2.4 LIMITATIONS OF EXISTING APPROACHES
A critical synthesis of the literature reviewed in Sections 2.1 through 2.3 reveals five systemic gaps that prevent existing academic frameworks from achieving production readiness in enterprise cloud RAG environments:

Fragmented Security Guarantees: Existing architectures treat confidentiality, integrity, and completeness as mutually exclusive design goals. Distance-preserving encryption schemes such as ppRAG [21] protect vector confidentiality against Vec2Text inversion [5] but provide zero defense against active chunk tampering or server-side partition dropping.
Symmetric Trust Misalignment in ZKP Systems: Frameworks such as VeriRAG [7], V3DB [8], and zkRAG [9] assume a verifier with zero local storage capacity, forcing the untrusted cloud server to prove every floating-point multiplication inside an R1CS arithmetic circuit. In realistic enterprise deployments, the client gateway possesses sufficient local memory (tens of megabytes) to retain a 32-byte Merkle root and coarse Voronoi centroids, making heavy zero-knowledge circuit compilation entirely unnecessary.
Vulnerability to Lazy-Cloud Cluster Omission: Partitioned ANN indices (IVF and HNSW) rely on multi-probe heuristics [2, 3]. Neither edge-cloud split architectures nor Merkle tree document stores verify whether the cloud server actually probed all required geometric boundary partitions, allowing cost-cutting cloud providers to silently degrade search recall.
Rebalancing Bottlenecks in Static Merkle Trees: Conventional verifiable databases bind records using balanced binary Merkle trees or static snapshots (as in V3DB [8]), which require expensive tree reconstructions or snapshot recompilations whenever new enterprise documents are ingested.
Absence of Multi-Tenant Cryptographic Isolation: Enterprise RAG deployments serve multiple organizational departments with strict access boundaries. Existing verifiable RAG schemes lack hierarchical tenant-to-enterprise cryptographic binding and fail to integrate pre-decryption access control with post-decryption hallucination filtering.

3.4 PHASE A: TWO-TIER MERKLE MOUNTAIN RANGE TRUST STRUCTURE BUILDER
Module 3 constructs an append-only Two-Tier Merkle Mountain Range (MMR) structure to bind document payloads and metadata into tamper-evident cryptographic commitments [12, 13]. 3.5 PHASE B: CLOUD MULTI-PROBE ANN SEARCH AND DYNAMIC BOUNDARY VALIDATION
In Phase B, Module 4 executes multi-probe ANN vector search over orthogonally masked vectors on the untrusted cloud vector database [2, 3]. To audit the search without relying on server-side zero-knowledge proofs, Module 5 executes Voronoi Dynamic Boundary Validation (DBV) within the client enclave. Because the client holds the coarse-quantizer centroids, it can compute the exact cosine distance from the query vector to every centroid and derive the set of cells that must be probed: every cell whose centroid lies within the dynamic margin r_margin = 1.5 × r_closest. Knowing which cells should be probed is not enough, because a lazy cloud could simply report every required cell ID without scanning anything. DBV therefore requires verifiable evidence for each required cell.
Evidence returned by the cloud: the cloud keeps, for every IVF cell, a membership list committed under the MMR whose root the client holds. For each probed cell it returns that cell's best-scoring candidate together with an inclusion proof against the cell's committed membership, and the client checks that every required cell has valid evidence and that the returned top-K is consistent with the per-cell candidates. Optionally, the client also issues random spot-check challenges to cells it has chosen at random. 
Scope of the guarantee: DBV verifies protocol compliance — that the agreed set of cells was probed and evidenced — not that the exact global top-K was returned. A margin of 1.5 × d_min does not by itself guarantee that all true top-K neighbours lie in the checked cells, so recall is measured empirically (Section 5.3). HNSW graphs have no Voronoi cells, so DBV applies only to IVF-partitioned indices; the HNSW backend is used without the DBV check.
3.6 PHASE B: FIVE-GATE SEQUENTIAL CLIENT VERIFIER AND GROUNDED SYNTHESIS
Module 6 enforces a deterministic five-gate verifier before releasing candidate passages to the generative LLM [14, 15]: Gate 1 verifies HMAC-signed session tokens carrying tenant and role claims; Gate 2 audits Two-Tier MMR inclusion proofs against local root R_ent; Gate 3 checks Voronoi DBV cell coverage; Gate 4 validates AES-256-GCM 128-bit GMAC tags; and Gate 5 evaluates CRAG relevance and Self-RAG reflection scores [14, 15]. Responses passing all five gates are decrypted and injected into the LLM context window for grounded answer generation [14, 15].
Tenant isolation on the cloud side: each tenant's vectors are stored in a separate collection, and the cloud rejects any search whose token does not authorize that collection, so that other tenants' data is never searched; Gate 1 then confirms on the client that every returned chunk belongs to the requesting tenant. 
CHAPTER 4: MATHEMATICAL FORMULATIONS AND SECURITY ANALYSIS
4.1 ISOMETRIC ORTHOGONAL VECTOR MASKING AND INNER-PRODUCT PRESERVATION
To protect semantic vectors against embedding inversion attacks such as Vec2Text while enabling low-latency similarity evaluation on untrusted cloud servers, the client enclave applies an isometric orthogonal transformation matrix Q in O(384) derived via Householder QR decomposition, paired with a secret coordinate permutation matrix P_π [18]. For any dense embedding vector v in ℝᵈ, the masked vector v' = P_π Q v strictly preserves Euclidean norms and inner products, satisfying Equation (4.1):
⟨u', v'⟩ = (P_π Q u)ᵀ (P_π Q v) = uᵀ Qᵀ (P_πᵀ P_π) Q v = uᵀ Qᵀ I_d Q v = uᵀ I_d v = ⟨u, v⟩(4.1)
Consequently, cosine similarity rankings on the cloud remain identical to those in the unencrypted domain [18]. Table 4.1 summarizes the mathematical notation and cryptographic parameters utilized across the verification engine [11, 18].
Security scope of the masking: because P_π is itself orthogonal, the product P_π Q is just another orthogonal matrix, so the permutation adds no security beyond that of Q alone. The masking protects against an adversary who sees only masked data (a ciphertext-only model). It does not protect against a known-plaintext attack: an insider who can embed about d = 384 documents known to be in the corpus (for example public policies or templates) obtains 384 pairs of original and masked vectors, from which Q can be recovered by orthogonal Procrustes analysis in milliseconds; every stored vector can then be unmasked and passed to an inversion attack such as Vec2Text [5]. In addition, the cloud still observes every pairwise similarity and the masked centroids, which leaks cluster structure. Noisy schemes such as approximate distance-comparison-preserving encryption (DCPE) are a possible mitigation at some cost in recall.

4.2 TWO-TIER MERKLE MOUNTAIN RANGE INCLUSION PROOF CONSTRUCTION
To guarantee payload authenticity without server-side zero-knowledge arithmetic circuits, the framework maintains an append-only Two-Tier Merkle Mountain Range (MMR) [12, 13]. Tier 1 comprises per-tenant User MMRs whose peak hashes are bagged into a global Tier 2 Cloud Enterprise MMR anchored by a 32-byte master root R_ent held strictly inside the client enclave [12, 13]. Figure 3.3 illustrates the structural peak bagging and hierarchy linking tenant MMRs to the master enterprise root [12, 13].
Leaf binding: each child chunk is bound to its tenant's MMR by the leaf digest of Equation (4.2), which hashes the chunk identifiers and the plaintext hash under a domain-separation tag; an inclusion proof is the list of sibling hashes from the leaf to its mountain peak, followed by the other peaks needed to bag the root (O(log N) hashes). 
leaf = SHA-256("LEAF_v1" ‖ tenant_id ‖ chunk_id ‖ H(plaintext))(4.2)
Associated data: AES-256-GCM is invoked with (tenant_id ‖ chunk_id) as associated data, so a valid ciphertext cannot be moved into another chunk's slot or another tenant's collection without invalidating its GMAC tag. 
Updates and rollback detection: after each ingestion batch the client appends the new leaves, recomputes R_ent and stores it locally together with a monotonically increasing epoch number. Every cloud response carries the MMR size and epoch it was computed under; the client rejects a response with an epoch lower than the stored one (replay of an older state) and checks with an append-only consistency proof that the old root is a prefix of the new one. 
4.3 VORONOI DYNAMIC BOUNDARY VALIDATION (DBV) FORMULATION
To audit whether an untrusted cloud vector database executes complete multi-probe searches across partitioned Inverted File (IVF) cells without lazily dropping adjacent clusters, the framework formulates Voronoi Dynamic Boundary Validation (DBV). Given a query vector q and coarse-quantizer centroids {μ_1, ..., μ_C}, the client computes exact cosine distances to all centroids locally. Equation (4.3) enforces a dynamic margin expansion threshold, where d(q, μ) = 1 − cos(q, μ) is the cosine distance and r_closest is the distance to the nearest centroid:
r_margin = 1.5 × r_closest,   r_closest = min_i d(q, μ_i),   d(q, μ) = 1 − cos(q, μ)(4.3)
Figure 4.1 illustrates the geometry of Voronoi DBV boundary auditing. The set of required cells is S_req = { i : d(q, μ_i) ≤ r_margin }, and the verifier accepts a response only if every cell in S_req carries valid evidence (Section 3.5).

4.4 FORMAL SECURITY ANALYSIS AGAINST ADVERSARIAL THREAT CAPABILITIES
The sequential five-gate client verifier maps directly to the five adversarial threat vectors (TV-01 through TV-05) identified in Section 1.2 (see Figure 4.2):
Gate 1 (RBAC Tenant Isolation): Validates cryptographic authorization tokens to block cross-tenant privilege escalation (TV-04).
Gate 2 (Two-Tier MMR Integrity): Audits inclusion proofs against local root R_ent to detect bit-level chunk forgery and cross-document splicing (TV-02) [12].
Gate 3 (Voronoi DBV Completeness): Verifies multi-probe cell coverage to neutralize lazy-cloud cluster omission (TV-03).
Gate 4 (AES-256-GCM AEAD Decryption): Validates 128-bit GMAC tags prior to plaintext release, detecting any modification of the ciphertext or its associated data (TV-02) [11]. Eavesdropping and inversion (TV-01) are addressed by the orthogonal masking and AES-256-GCM encryption applied at ingestion, not by this gate.
Gate 5 (CRAG / Self-RAG Grounding): Evaluates the semantic relevance of the verified chunks before they are passed to the generative LLM, filtering irrelevant context [14, 15].  TV-05 is addressed by the design as a whole, which replaces server-side zero-knowledge proving with client-side verification, not by this gate.

5.4 DISCUSSION OF EXPERIMENTAL FINDINGS, LIMITATIONS, AND CONCLUSION
System Limitations: (i) Dynamic Centroid Maintenance: Periodic K-Means re-clustering is required as the corpus expands by orders of magnitude; (ii) Text-Only Vector Scope: Current orthogonal transformations are optimized for 384-dimensional text embeddings, with multi-modal expansion designated for future work [10].
Additional limitations: (iii) Known-plaintext attack on the masking: an insider who embeds about 384 documents known to be in the corpus obtains enough original–masked pairs to recover Q by orthogonal Procrustes analysis, after which every stored vector can be unmasked; the guarantee therefore holds only in a ciphertext-only model, and noisy schemes such as approximate distance-comparison-preserving encryption (DCPE) are a possible mitigation. (iv) Leakage to the cloud: the cloud observes access patterns, all pairwise similarities between masked vectors and the masked centroids, which leaks cluster structure. (v) Trust placed in the client: all keys and the root R_ent reside in the client enclave, so a compromised client defeats the scheme. (vi) Freshness: the client must detect rollback of the MMR state to an older root (Section 4.2).
Conclusion: The Asymmetric Verification Framework suggests, on the four scenarios evaluated here, that an enterprise cloud RAG system can obtain confidentiality against a ciphertext-only adversary, tamper-evident integrity and probed-cell compliance checking without zero-knowledge proving, at a client-side verification cost of a few milliseconds. The prototype is a foundation for further work on secure enterprise RAG rather than a production-ready system.
